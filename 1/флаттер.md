# Сценарий доклада: CI/CD Flutter-приложений для ОС Аврора

**Версия:** практический сценарий без повторов и без «красивых» пустых оборотов  
**Задача:** сохранить теорию, объяснение кода и логику обновлённой презентации, но говорить только то, что помогает понять процесс.

---

## Как читать этот сценарий

Некоторые темы в презентации раскрываются через несколько слайдов подряд: регистрация runner, build job, sign job, Docker Runner. В этих местах не нужно каждый раз заново объяснять всю команду. Говорим только то, что появилось на текущем слайде.

Правило для выступления:

- новый термин — даём определение;
- новый фрагмент кода — объясняем строки, которые появились;
- слайд с результатом — фиксируем, что получили, и переходим дальше;
- если мысль уже прозвучала — не повторяем её другими словами.

Основная линия доклада: есть Flutter-проект под ОС Аврора. Ручная сборка сначала работает, но в командной разработке начинает мешать. Поэтому сборку, подпись и проверку переносим в GitLab CI. Потом отдельно фиксируем сборочное окружение через Docker.

# 2. ОС Аврора и особенности сборки

## Слайд 6. Что такое ОС Аврора

ОС Аврора — отечественная операционная система для мобильных устройств и планшетов. Она построена на Linux-стеке.

Для разработчика это отдельная target-платформа. Значит, у неё есть:

- собственные SDK;
- системные API;
- формат пакета;
- правила совместимости с версией ОС.

В рамках доклада нас интересует именно сборочный вывод: Flutter-приложение должно превратиться в пакет, который понимает ОС Аврора.

---

## Слайд 7. Чем Аврора отличается

Аврора рассчитана на использование в управляемой корпоративной среде. Поэтому в системе важны:

- политики безопасности;
- контроль прав доступа;
- сертификаты;
- администрирование устройств;
- интеграция с корпоративными сервисами.

Для сборки приложения это влияет на результат. Пакет должен быть подготовлен в нужном формате, подписан подходящим профилем и проверен перед передачей дальше.

---

## Слайд 8. Аврора для разработчика

Для разработчика Аврора проявляется через набор инструментов:

- SDK;
- PSDK;
- эмулятор;
- системные API;
- правила сборки и совместимости.

Если человек приходит из обычной Flutter-разработки, ему нужно учитывать дополнительный платформенный слой. Dart-код и Flutter UI остаются, но сборка должна учитывать требования Авроры.

---

## Слайд 9. Где здесь Flutter

Flutter используется для UI и основной логики приложения. На Dart пишутся виджеты, состояние, зависимости и значительная часть бизнес-логики.

Кроссплатформенная часть сохраняется. Но при сборке под Аврору Flutter-проект передаётся в инструменты, которые умеют собирать приложение под эту платформу.

Короткая схема:

```text
Dart / Flutter UI → Flutter Aurora SDK → Aurora PSDK → RPM package
```

---

## Слайд 10. Почему сборка особенная

Особенности сборки под Аврору:

1. нужен Flutter Aurora SDK;
2. нужен Aurora PSDK;
3. нужно выбрать target-архитектуру;
4. результатом становится RPM-пакет;
5. пакет нужно подписать;
6. пакет нужно провалидировать.

Эти шаги неудобно держать как набор ручных команд. Дальше покажу, почему это становится проблемой в команде.

# 3. Почему ручная сборка мешает команде

## Слайд 11. Проблема ручной сборки

Типичная ситуация: один разработчик настроил машину, поставил SDK, прописал путь к PSDK, получил доступ к сертификатам и умеет собрать пакет локально.

Для одной проверки этого достаточно. Для командного процесса появляются проблемы:

- на разных машинах могут быть разные версии SDK и PSDK;
- локальные переменные и пути могут отличаться;
- порядок команд может быть описан в инструкции, но не выполняться автоматически;
- перед релизом можно забыть подпись или проверку.

Ручная сборка зависит от состояния конкретной машины и внимательности конкретного человека.

---

## Слайды 12–15. Боли команды

Эти слайды лучше рассказывать как одну цепочку, а не как четыре одинаковых пункта.

Первая проблема — разные версии инструментов. Один человек обновил Flutter Aurora SDK, другой работает со старой версией. Код одинаковый, окружение разное, результат может отличаться.

Вторая проблема — повторяемость. Если пакет был собран вручную, через несколько дней нужно восстановить: из какого commit он собран, какой PSDK использовался, какие переменные были выставлены, проходила ли подпись.

Третья проблема — обязательные шаги после сборки. RPM можно собрать, но забыть подписать. Можно подписать не тем профилем. Можно не запустить валидацию.

Четвёртая проблема — онбординг. Новому разработчику нужно поднять всю среду: установить зависимости, SDK, PSDK, прописать пути, проверить доступ к утилитам подписи и валидации. На это уходит время, и часть ошибок появляется ещё до работы с кодом приложения.

Эти проблемы решаются не устными инструкциями, а переносом процесса в CI.

---

## Слайд 16. Переход к решению

Сборку нужно описать как код.

Для GitLab CI это файл `.gitlab-ci.yml`. В нём указываются:

- stages;
- jobs;
- команды;
- runner tags;
- зависимости между job;
- артефакты, которые нужно сохранить.

После этого GitLab CI запускает одинаковый процесс для commit или merge request.

# 4. CI/CD

## Слайд 17. Что такое CI/CD

CI/CD — это Continuous Integration и Continuous Delivery.

CI, Continuous Integration, означает непрерывную интеграцию. Изменения регулярно попадают в общий репозиторий и автоматически проверяются.

CD, Continuous Delivery, означает непрерывную доставку. Приложение автоматически готовится к следующему этапу: тестированию, внутреннему релизу, передаче заказчику или публикации в хранилище артефактов.

В этом докладе CI/CD используется для автоматизации трёх действий: сборки RPM, подписи RPM и валидации RPM.

---

## Слайд 18. CI: непрерывная интеграция

CI даёт быструю проверку изменений.

Разработчик отправляет commit или merge request. Pipeline запускается автоматически. Если сборка падает, ошибка видна в GitLab: в какой job, на какой команде и с каким логом.

Для Flutter под Аврору это полезно, потому что ошибка может быть не только в Dart-коде. Она может быть в зависимостях, платформенной части, target-архитектуре или сборочном окружении.

---

## Слайд 19. CD: непрерывная доставка

В этом докладе CD — это подготовка пакета к следующему этапу.

После успешной сборки pipeline выполняет подпись и валидацию. Результат сохраняется как артефакт GitLab CI.

Такой пакет можно передавать тестировщикам, использовать для демонстрации или включать в следующий релизный процесс.

---

## Слайд 20. Зачем CI/CD команде

CI/CD нужен команде по конкретным причинам:

- все запускают один и тот же процесс;
- правила сборки лежат в репозитории;
- результат связан с commit;
- логи доступны в GitLab;
- артефакт можно скачать из pipeline;
- обязательные шаги не держатся в памяти человека.

Это уменьшает количество ошибок, которые появляются из-за ручных действий.

---

## Слайд 21. Что именно автоматизируем

Автоматизируем три этапа:

```text
build → sign → validation
```

`build` собирает RPM-пакет.

`sign` подписывает пакет выбранным профилем.

`validation` проверяет итоговый пакет и сохраняет результат в pipeline artifacts.

# 5. Компоненты сборки

## Слайд 22. Основные компоненты сборки

Для сборки Flutter-приложения под ОС Аврора нужны два основных компонента:

- Flutter Aurora SDK;
- Aurora PSDK.

Flutter Aurora SDK отвечает за поддержку Авроры со стороны Flutter.

Aurora PSDK отвечает за платформенную сборку под конкретную версию ОС и архитектуру.

---

## Слайд 23. Flutter Aurora SDK

Flutter Aurora SDK добавляет в Flutter поддержку ОС Аврора.

Он даёт:

- target-платформу Аврора;
- команды сборки;
- структуру проекта под Аврору;
- интеграцию с нативной частью приложения.

Через него выполняются обычные Flutter-действия: получение зависимостей, работа с Dart-кодом и запуск сборки.

Пример команды, которая дальше будет в build job:

```bash
flutter-aurora build aurora --release --target-platform aurora-arm64
```

---

## Слайд 24. Aurora PSDK

Aurora PSDK — платформенное сборочное окружение ОС Аврора.

В него входят:

- chroot-окружение;
- toolchain;
- системные библиотеки;
- target-окружения для архитектур.

PSDK нужен, чтобы приложение собиралось под конкретную версию ОС Аврора и конкретную архитектуру устройства.

---

## Слайд 25. Target-архитектуры

В сборке могут использоваться target-архитектуры:

```text
aarch64
armv7hl
x86_64
```

В примерах доклада используется `aarch64`, для Flutter-команды это target-платформа `aurora-arm64`.

Pipeline можно расширить под несколько архитектур, добавив отдельные build job.

---

## Слайд 26. Как SDK и PSDK связаны

Flutter Aurora SDK должен знать путь к установленному PSDK.

Настройка выполняется командой:

```bash
flutter-aurora config --aurora-psdk-dir /path/to/AuroraPlatformSDK/sdks/aurora_psdk
```

Команда записывает путь к PSDK в конфигурацию Flutter Aurora SDK. После этого сборочные команды могут использовать платформенное окружение Авроры.

Если путь не указан или указан неверно, сборка под Аврору не пройдёт корректно.

---

## Слайд 27. Схема сборки приложения

Схема сборки:

```text
Flutter project → Flutter Aurora SDK → Aurora PSDK → RPM package
```

`Flutter project` содержит Dart-код, UI, зависимости и платформенную часть.

`Flutter Aurora SDK` запускает сборку под Аврору.

`Aurora PSDK` обеспечивает сборку под версию ОС и архитектуру.

`RPM package` — итоговый пакет, который дальше подписывается и проходит валидацию.

# 6. Подготовка GitLab CI окружения

## Слайд 28. Где запускается CI

Pipeline выполняется на машине, где установлен GitLab Runner.

Это может быть выделенный Linux-сервер или виртуальная машина.

На первом этапе можно использовать `shell executor`: job запускается прямо на хосте, а нужные инструменты заранее установлены на сервер.

Позже этот вариант будет заменён Docker executor, чтобы зафиксировать окружение в образе.

---

## Слайд 29. Что устанавливаем на сервер

На сервер устанавливаются:

- системные зависимости;
- Flutter Aurora SDK;
- Aurora Platform SDK / PSDK;
- утилиты подписи;
- утилиты валидации пакетов.

Роли компонентов:

- системные зависимости нужны для работы команд и установщиков;
- Flutter Aurora SDK запускает Flutter-сборку под Аврору;
- PSDK выполняет платформенную часть сборки;
- утилиты подписи подписывают RPM;
- валидатор проверяет готовый пакет.

---

## Слайд 30. Главный шаг настройки

После установки нужно связать Flutter Aurora SDK с PSDK:

```bash
flutter-aurora config --aurora-psdk-dir /path/to/AuroraPlatformSDK/sdks/aurora_psdk
```

Эту настройку нужно выполнить до запуска pipeline. Иначе build job не сможет использовать PSDK.

В варианте с shell runner эта настройка выполняется на сервере. В варианте с Docker она переносится в Dockerfile.

---

## Слайд 31. Кто выполняет pipeline

Pipeline выполняет GitLab Runner.

GitLab Runner — компонент, который получает job от GitLab CI и запускает её на конкретной машине или в контейнере.

GitLab хранит репозиторий и показывает состояние pipeline. Runner выполняет команды из `.gitlab-ci.yml`.

---

## Слайд 32. Что такое job

Job — отдельный шаг процесса, описанный в `.gitlab-ci.yml`.

В этом pipeline будут три основные job:

- build job — собрать RPM;
- sign job — подписать RPM;
- validation job — проверить RPM.

Если одна job падает, следующие этапы не запускаются.

---

## Слайды 33–38. Регистрация runner

Команда регистрации runner показывается в презентации постепенно. При выступлении объясняем только новую строку.

Начало регистрации:

```bash
sudo gitlab-runner register \
```

Команда запускает процесс регистрации runner на сервере.

Адрес GitLab:

```bash
sudo gitlab-runner register \
  --url https://gitlab.com/ \
```

`--url` указывает GitLab-инстанс, к которому подключается runner.

Токен регистрации:

```bash
sudo gitlab-runner register \
  --url https://gitlab.com/ \
  --registration-token <TOKEN> \
```

`--registration-token` разрешает подключить runner к проекту или группе.

Имя runner:

```bash
sudo gitlab-runner register \
  --url https://gitlab.com/ \
  --registration-token <TOKEN> \
  --name aurora_flutter_runner \
```

`--name` помогает отличать этот runner в интерфейсе GitLab.

Executor:

```bash
sudo gitlab-runner register \
  --url https://gitlab.com/ \
  --registration-token <TOKEN> \
  --name aurora_flutter_runner \
  --executor shell \
```

`shell` означает, что job будет запускаться в оболочке сервера.

Tag runner:

```bash
sudo gitlab-runner register \
  --url https://gitlab.com/ \                        # адрес Git-платформы
  --registration-token <TOKEN> \                     # токен регистрации
  --name aurora_flutter_runner \                     # имя runner’а
  --executor shell \                                 # запуск jobs на хосте
  --tag-list aurora_flutter_runner                   # привязка jobs к нужному runner’у
```

`--tag-list` нужен, чтобы GitLab отправлял job на runner с нужным окружением.

---

## Слайд 39. Зачем нужны tags

Tags связывают job с конкретным runner.

В `.gitlab-ci.yml` указываем:

```yaml
tags:
  - aurora_flutter_runner
```

GitLab ищет runner с таким tag и отправляет job туда.

Для сборки под Аврору это нужно, потому что job должна попасть на сервер, где есть Flutter Aurora SDK, PSDK и утилиты подписи.

---

## Слайд 40. Сохранение настроек

После регистрации параметры runner сохраняются в `config.toml`:

```toml
[[runners]]
name = "aurora_psdk_runner"
url = "https://gitlab.com/"
executor = "shell"
```

Здесь видно имя runner, GitLab URL и executor.

`executor = "shell"` означает запуск команд прямо на сервере.

# 7. Pipeline и `.gitlab-ci.yml`

## Слайд 41. Что такое pipeline

Pipeline — последовательность автоматических шагов, которые GitLab CI выполняет над проектом.

Он запускается при commit или merge request.

Описание pipeline лежит в `.gitlab-ci.yml` рядом с исходным кодом.

---

## Слайд 42. Файл `.gitlab-ci.yml`

`.gitlab-ci.yml` описывает:

- stages;
- jobs;
- команды;
- tags runner;
- зависимости между job;
- artifacts.

Файл версионируется вместе с кодом. Если меняется процесс сборки, это изменение попадает в историю Git.

---

## Слайд 43. Общая схема процесса

Общая схема:

```text
Commit / Merge Request → GitLab CI → Runner → SDK → Pipeline → Artifacts
```

К этому моменту мы уже разобрали GitLab CI, runner и SDK. Дальше переходим к содержимому pipeline.

---

## Слайд 44. Три основные стадии

Pipeline состоит из трёх стадий:

```yaml
stages:
  - build
  - sign
  - validation
```

`build` собирает RPM-пакет.

`sign` подписывает RPM.

`validation` проверяет подписанный RPM.

Порядок важен: подпись запускается после сборки, валидация запускается после подписи.

---

## Слайд 45. Почему разделяем этапы

Разделение этапов упрощает отладку.

Если проблема в сборке, смотрим build job.

Если проблема в ключе, сертификате или профиле подписи, смотрим sign job.

Если пакет не проходит требования платформы, смотрим validation job.

Ещё один плюс: позже можно добавить сборку под другую архитектуру, не смешивая её с подписью и валидацией.

# 8. Build job

## Слайды 46–50. Build job

Build job собирает Flutter-приложение под `aarch64` и сохраняет RPM в artifacts.

Сначала задаём имя job, stage, runner tag и artifacts:

```yaml
"build-aurora-flutter_aarch64":
  stage: build
  tags:
    - aurora_flutter_runner
  artifacts:
    paths:
      - ./artifacts/*.rpm
```

Разбор:

- `build-aurora-flutter_aarch64` — имя job;
- `stage: build` — job относится к стадии сборки;
- `tags` — job должна выполняться на runner с нужным окружением;
- `artifacts.paths` — GitLab сохранит RPM-файлы из `./artifacts/`.

Добавляем команды:

```yaml
  script:
    - mkdir -p artifacts
```

`mkdir -p artifacts` создаёт каталог для RPM-файлов.

```yaml
    - /flutter-aurora/bin/flutter pub get
```

`flutter pub get` получает зависимости из `pubspec.yaml`.

```yaml
    - /flutter-aurora/bin/flutter build aurora --release --target-platform aurora-arm64
```

Эта команда запускает сборку под ОС Аврора:

- `build aurora` — сборка под платформу Аврора;
- `--release` — release-сборка;
- `--target-platform aurora-arm64` — target под `aarch64`.

```yaml
    - cp build/aurora/psdk_${PSDK_VER}/aurora-arm64/release/RPMS/*.rpm ./artifacts/
```

Команда копирует готовые RPM-пакеты в каталог artifacts.

`${PSDK_VER}` используется в пути к результатам сборки, потому что каталог содержит версию PSDK.

Полная build job:

```yaml
"build-aurora-flutter_aarch64":
  stage: build
  tags:
    - aurora_flutter_runner
  artifacts:
    paths:
      - ./artifacts/*.rpm
  script:
    - mkdir -p artifacts
    - /flutter-aurora/bin/flutter pub get
    - /flutter-aurora/bin/flutter build aurora --release --target-platform aurora-arm64
    - cp build/aurora/psdk_${PSDK_VER}/aurora-arm64/release/RPMS/*.rpm ./artifacts/
```

После этой job в GitLab artifacts появляется неподписанный RPM.

## Слайд 51. Задание переменной `PSDK_VER`

Версию PSDK удобно вынести в переменную:

```yaml
variables:
  PSDK_VER: "<psdk_version>"
```

Если версия PSDK меняется, её можно поменять в одном месте, а не искать внутри путей в script.

Он ещё не подписан и не проверен. Поэтому следующий этап — sign.

# 9. Sign job

## Слайды 53–54. Sign job

Sign job берёт RPM из build job и подписывает его.

Каркас job:

```yaml
"sign-aurora-flutter_aarch64":
  stage: sign
  tags:
    - aurora_flutter_runner
  needs:
    - "build-aurora-flutter_aarch64"
  dependencies:
    - "build-aurora-flutter_aarch64"
  artifacts:
    paths:
      - ./artifacts/*.rpm
```

Разбор:

- `stage: sign` — стадия подписи;
- `needs` — sign запускается после успешного build;
- `dependencies` — sign получает artifacts из build job;
- `artifacts` — подписанный RPM снова сохраняется в artifacts.

Команда подписи:

```yaml
  script:
    - /path/to/AuroraPlatformSDK/sdks/sdk-chroot rpmsign-external sign
      -k ~/aurora-profiles/${SIGN_PROFILE}/key.pem
      -c ~/aurora-profiles/${SIGN_PROFILE}/cert.pem
      ./artifacts/*.rpm
```

Разбор команды:

- `sdk-chroot` запускается из Aurora Platform SDK;
- `rpmsign-external sign` выполняет подпись RPM;
- `-k` передаёт приватный ключ;
- `-c` передаёт сертификат;
- `./artifacts/*.rpm` задаёт пакеты для подписи.

Полная sign job:

```yaml
"sign-aurora-flutter_aarch64":
  stage: sign
  tags:
    - aurora_flutter_runner
  needs:
    - "build-aurora-flutter_aarch64"
  dependencies:
    - "build-aurora-flutter_aarch64"
  artifacts:
    paths:
      - ./artifacts/*.rpm
  script:
    - /path/to/AuroraPlatformSDK/sdks/sdk-chroot rpmsign-external sign
      -k ~/aurora-profiles/${SIGN_PROFILE}/key.pem
      -c ~/aurora-profiles/${SIGN_PROFILE}/cert.pem
      ./artifacts/*.rpm
```

После этой job RPM остаётся в artifacts, но уже с подписью.

---

## Слайд 55. Профиль подписи

Профиль подписи определяет, каким ключом и сертификатом подписывается пакет.

Возможные профили из презентации:

```text
Regular
Extended
Mdm
Antivirus
Auth
```

Профиль можно задать переменной:

```yaml
variables:
  SIGN_PROFILE: "Regular"
```

Тогда пути к ключу и сертификату строятся через `${SIGN_PROFILE}`:

```bash
~/aurora-profiles/${SIGN_PROFILE}/key.pem
~/aurora-profiles/${SIGN_PROFILE}/cert.pem
```

Так профиль подписи виден в настройках pipeline или переменных проекта.

---

## Слайд 56. Кладём профиль подписи

На runner должен быть доступ к файлам профиля подписи.

Пример структуры:

```text
~/aurora-profiles/Regular/key.pem
~/aurora-profiles/Regular/cert.pem
```

Приватные ключи не нужно хранить в репозитории. Их нужно хранить отдельно и выдавать runner доступ только к нужным файлам.

# 10. Validation job

## Слайд 58. Validation job

Validation job проверяет подписанный RPM:

```yaml
"validation-aurora-flutter_aarch64":
  stage: validation
  tags:
    - aurora_flutter_runner
  needs: ["sign-aurora-flutter_aarch64"]
  dependencies:
    - "sign-aurora-flutter_aarch64"
  script:
    - /path/to/rpm_validator /path/to/AuroraPlatformSDK/ ./artifacts/*.rpm
```

Разбор:

- `stage: validation` — стадия проверки;
- `needs` — запуск после sign job;
- `dependencies` — получение artifacts из sign job;
- `rpm_validator` — утилита проверки RPM;
- `/path/to/AuroraPlatformSDK/` — путь к Aurora Platform SDK;
- `./artifacts/*.rpm` — проверяемые пакеты.

Валидация проверяет, что пакет корректно собран, содержит ожидаемые метаданные и соответствует требованиям платформы.

В GitLab остаются логи каждой job: по ним можно увидеть, где был собран пакет, какой commit запускал pipeline и на каком шаге возникла ошибка, если она была.

# 12. Docker

## Слайд 61. Почему нужен Docker

Docker нужен, чтобы описать сборочное окружение в Dockerfile.

В образ можно заранее положить:

- системные зависимости;
- Aurora PSDK;
- Flutter Aurora SDK;
- настройку связи Flutter Aurora SDK с PSDK.

После этого job запускается внутри контейнера из подготовленного образа.

Если нужно обновить SDK, собирается новый образ. Если нужно вернуться к предыдущей версии, используется предыдущий tag образа.

---

## Слайд 62. Что такое Docker-образ

Docker-образ — неизменяемый шаблон среды выполнения.

Он содержит файловую систему, зависимости, переменные окружения и инструкции запуска.

На основе образа создаётся контейнер. В контейнере выполняются команды pipeline.

Для этой задачи Docker-образ фиксирует версии Ubuntu, системных зависимостей, Aurora PSDK, Flutter Aurora SDK и базовую настройку между ними.

---

## Слайды 63–65. Три преимущества Docker

Эти слайды лучше объяснять через проблему shell runner: окружение хранится на сервере.

Первое преимущество — воспроизводимость. Один и тот же код собирается в одном и том же образе.

Второе — изоляция. Инструменты сборки находятся в контейнере и меньше засоряют хост-систему.

Третье — версионирование. Разные версии сборочного окружения можно хранить как разные tags:

```text
flutter-aurora:psdk-5.1
flutter-aurora:psdk-5.2
flutter-aurora:latest
```

Это полезно, если нужно поддерживать несколько версий PSDK или безопасно проверять обновление инструментов.

---

# 13. Dockerfile

## Слайд 66. Dockerfile: общая идея

Dockerfile описывает сборочную среду.

Внутри образа должны быть:

- базовая ОС;
- системные зависимости;
- Aurora PSDK;
- Flutter Aurora SDK;
- настройка `flutter-aurora config --aurora-psdk-dir`.

Дальше Dockerfile разбирается по частям.

---

## Слайд 67. Dockerfile: настройка окружения

Первая часть задаёт базовый образ, переменные окружения и системные зависимости:

```dockerfile
FROM ubuntu:22.04

ENV HOME="/home/docker"
ENV PATH="$HOME/.local/opt/flutter-aurora/bin:$HOME/.local/bin:$PATH"

RUN apt-get update && \
    apt-get install -y --no-install-recommends sudo git openssh-client ca-certificates tar unzip bzip2 xz-utils && \
    rm -rf /var/lib/apt/lists/*
```

Разбор:

- `FROM ubuntu:22.04` задаёт базовую ОС;
- `ENV HOME="/home/docker"` задаёт домашнюю директорию пользователя;
- `ENV PATH=...` добавляет пути к Flutter Aurora SDK и локальным бинарникам;
- `apt-get install` устанавливает зависимости для работы Git, SSH, сертификатов и архивов;
- `rm -rf /var/lib/apt/lists/*` очищает apt-кэш.

---

## Слайд 68. Dockerfile: пользователь

Следующий блок создаёт пользователя `docker`:

```dockerfile
RUN useradd -rm -d $HOME -s /bin/bash -g root -G sudo -u 1001 docker && \
    echo 'docker ALL=(ALL) NOPASSWD:ALL' > /etc/sudoers.d/docker && \
    chmod 0440 /etc/sudoers.d/docker

USER docker
WORKDIR $HOME
```

Разбор:

- `useradd` создаёт пользователя с домашней директорией `$HOME`;
- запись в `/etc/sudoers.d/docker` даёт sudo без пароля;
- `chmod 0440` выставляет правильные права на sudoers-файл;
- `USER docker` переключает дальнейшие команды на этого пользователя;
- `WORKDIR $HOME` задаёт рабочий каталог.

Так сборка выполняется в пользовательском окружении, а не постоянно от root.

---

## Слайд 69. Dockerfile: установка SDK

Этот блок копирует установщики, устанавливает PSDK и Flutter Aurora SDK:

```dockerfile
COPY --chown=docker:root installers/ /tmp/installers/

RUN sudo /bin/bash /tmp/installers/install_aurora_psdk.sh \
    --input-dir /tmp/installers/AuroraPlatformSDK \
    --install-dir $HOME/AuroraPlatformSDK

RUN mkdir -p "$HOME/.local/opt/flutter-aurora" "$HOME/.local/bin" && \
    tar -xf /tmp/installers/flutter-aurora.tar.xz \
      --strip-components=1 \
      -C "$HOME/.local/opt/flutter-aurora" && \
    ln -s "$HOME/.local/opt/flutter-aurora/bin/flutter" "$HOME/.local/bin/flutter-aurora" && \
    flutter-aurora config --aurora-psdk-dir "$HOME/AuroraPlatformSDK/sdks/aurora_psdk"
```

Разбор:

- `COPY --chown=docker:root installers/ /tmp/installers/` копирует установочные файлы в образ;
- `install_aurora_psdk.sh` устанавливает Aurora PSDK;
- `--input-dir` указывает каталог с установщиками PSDK;
- `--install-dir` указывает каталог установки;
- `mkdir -p` создаёт каталоги для Flutter Aurora SDK и локальных бинарников;
- `tar -xf` распаковывает архив Flutter Aurora SDK;
- `--strip-components=1` убирает верхний уровень каталогов из архива;
- `ln -s` создаёт команду `flutter-aurora` в `$HOME/.local/bin`;
- `flutter-aurora config --aurora-psdk-dir ...` связывает Flutter Aurora SDK с установленным PSDK.

Полный Dockerfile:

```dockerfile
FROM ubuntu:22.04

ENV HOME="/home/docker"
ENV PATH="$HOME/.local/opt/flutter-aurora/bin:$HOME/.local/bin:$PATH"

RUN apt-get update && \
    apt-get install -y --no-install-recommends sudo git openssh-client ca-certificates tar unzip bzip2 xz-utils && \
    rm -rf /var/lib/apt/lists/*

RUN useradd -rm -d $HOME -s /bin/bash -g root -G sudo -u 1001 docker && \
    echo 'docker ALL=(ALL) NOPASSWD:ALL' > /etc/sudoers.d/docker && \
    chmod 0440 /etc/sudoers.d/docker

USER docker
WORKDIR $HOME

COPY --chown=docker:root installers/ /tmp/installers/

RUN sudo /bin/bash /tmp/installers/install_aurora_psdk.sh \
    --input-dir /tmp/installers/AuroraPlatformSDK \
    --install-dir $HOME/AuroraPlatformSDK

RUN mkdir -p "$HOME/.local/opt/flutter-aurora" "$HOME/.local/bin" && \
    tar -xf /tmp/installers/flutter-aurora.tar.xz \
      --strip-components=1 \
      -C "$HOME/.local/opt/flutter-aurora" && \
    ln -s "$HOME/.local/opt/flutter-aurora/bin/flutter" "$HOME/.local/bin/flutter-aurora" && \
    flutter-aurora config --aurora-psdk-dir "$HOME/AuroraPlatformSDK/sdks/aurora_psdk"
```

## Слайд 70. GitLab Container Registry

После подготовки Dockerfile образ нужно собрать:

```bash
docker build -t registry.gitlab.com/<group>/<project>/flutter-aurora:latest .
```

Разбор:

- `docker build` собирает образ;
- `-t` задаёт имя и tag;
- `registry.gitlab.com/<group>/<project>/flutter-aurora:latest` — путь к образу в GitLab Container Registry;
- `.` означает, что Dockerfile и контекст сборки находятся в текущем каталоге.

Затем образ публикуется в registry:

```bash
docker push registry.gitlab.com/<group>/<project>/flutter-aurora:latest
```

После публикации его можно использовать в GitLab CI через поле `image`.

Для рабочих проектов лучше использовать не только `latest`, но и версионные tags.

# 14. Docker Runner

## Слайды 71–73. GitLab Runner с Docker executor

Runner можно настроить с Docker executor:

```toml
[[runners]]
  name = "aurora-docker"
  executor = "docker"
```

`executor = "docker"` означает, что job выполняется в контейнере.

Дальше включается привилегированный режим:

```toml
[[runners]]
  name = "aurora-docker"
  executor = "docker"

  [runners.docker]
    privileged = true                                                      # привилегированный режим
```

`privileged = true` нужен для работы частей PSDK и `sdk-chroot`, которым требуются расширенные права контейнера.

После этого пробрасываются ресурсы хоста:

```toml
[[runners]]
  name = "aurora-docker"
  executor = "docker"

  [runners.docker]
    privileged = true                                                      # привилегированный режим
    volumes = [                                                            # проброс ресурсов хоста
      "/lib/modules:/lib/modules:ro",                                      # модули ядра
      "/run/dbus/system_bus_socket:/run/dbus/system_bus_socket",           # системный D-Bus
      "/var/run/dbus:/var/run/dbus:ro",                                    # сокеты D-Bus
      "/etc/machine-id:/etc/machine-id:ro",                                # machine-id
      "/var/lib/dbus:/var/lib/dbus:ro"                                     # данные D-Bus
    ]
```

Эти volumes нужны, потому что при работе `sdk-chroot` контейнеру может потребоваться доступ к системным ресурсам хоста: модулям ядра, D-Bus и machine-id.

В `.gitlab-ci.yml` образ используется так:

```yaml
image:
  name: registry.gitlab.com/<group>/<project>/flutter-aurora:latest

"build-aurora-flutter_aarch64":
  stage: build
  tags:
    - aurora-docker
  before_script:
    - $PSDK_DIR/sdk-chroot sdk-assistant list
  script:
    - mkdir -p artifacts
    - flutter-aurora pub get
    - flutter-aurora build aurora --release --target-platform=aurora-arm64
    - cp build/aurora/psdk_${PSDK_VER}/aurora-arm64/release/RPMS/*.rpm ./artifacts/
```

Разбор:

- `image.name` задаёт Docker-образ для job;
- `tags: aurora-docker` отправляет job на runner с Docker executor;
- `before_script` проверяет доступность PSDK через `sdk-chroot`;
- в `script` используется команда `flutter-aurora` без полного пути, потому что PATH настроен в Dockerfile.

# 15. Итог

## Слайд 74. Итоговое решение

К концу настройки есть три части:

1. `.gitlab-ci.yml` описывает pipeline;
2. GitLab Runner выполняет job;
3. Docker-образ содержит сборочное окружение.

В pipeline остаются этапы:

```text
build → sign → validation
```

Артефакты сохраняются в GitLab. По логам можно проверить, что выполнялось на каждом шаге.

---

## Слайд 75. Финальный вывод

Ручная сборка заменяется описанным процессом.

Разработчик отправляет код в репозиторий. GitLab CI запускает pipeline. Runner выполняет сборку, подпись и валидацию. Готовый RPM сохраняется в artifacts.

Итоговая цепочка:

```text
ручная сборка → GitLab CI → build/sign/validation → Docker-образ → воспроизводимое окружение
```

На этом всё, спасибо за внимание.
