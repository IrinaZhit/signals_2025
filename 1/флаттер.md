То есть Аврора поддерживает разные подходы: нативную разработку, кроссплатформенную разработку и веб-сценарии. Дальше в докладе я буду рассматривать именно Flutter/Dart, потому что он позволяет сохранить единую кодовую базу и ускорить разработку мобильного интерфейса.

## Слайд 16. CI/CD

### Перенесённый текст из исходного документа

**Исходный документ, слайд 16. Что такое CI/CD**

CI/CD состоит из двух частей. CI, continuous integration, отвечает за автоматическую проверку изменений. CD, continuous delivery, отвечает за подготовку результата к следующему этапу. Для нашего случая это означает: изменение пришло в репозиторий, pipeline собрал RPM, подписал его и сохранил результат.

**Исходный документ, слайд 17. CI: непрерывная интеграция**

В CI каждое изменение проходит автоматическую проверку. Pipeline запускается после commit или merge request, и ошибка видна прямо в Git-платформе. Практический плюс в том, что разработчик получает обратную связь быстро: не через день на ручной проверке, а сразу после запуска сборки.

**Исходный документ, слайд 18. CD: непрерывная доставка**

CD отвечает за подготовку приложения к передаче дальше: на тестирование, релиз или во внутреннее хранилище. Важно, что команда получает не просто лог сборки, а готовый артефакт. Для Flutter под Аврору таким артефактом будет RPM-пакет, прошедший нужные этапы.

## Слайд 21. Что такое pipeline и файл .gitlab-ci.yml

### Перенесённый текст из исходного документа

**Исходный документ, слайд 39. Что такое pipeline**

Pipeline — это последовательность автоматических шагов, которые GitLab выполняет для проекта. Он запускается после commit или merge request и показывает состояние процесса: что прошло успешно, где возникла ошибка и какие файлы были сохранены как результат.

**Исходный документ, слайд 30. Что такое job**

Job — это отдельный шаг внутри pipeline. Например, сборка, подпись и валидация могут быть разными job. Каждая job описывается в файле .gitlab-ci.yml: там задаются стадия, runner, команды, зависимости и артефакты, которые нужно сохранить после выполнения.

**Исходный документ, слайд 40. Файл .gitlab-ci.yml**

Файл .gitlab-ci.yml — это инструкция для GitLab CI. В нём описываются stages, job, команды и артефакты. Главное преимущество в том, что pipeline версионируется вместе с кодом. Изменили процесс сборки — это изменение тоже видно в истории репозитория.

## Слайд 22. Где запускается CI

### Перенесённый текст из исходного документа

**Исходный документ, слайд 26. Где запускается CI**

CI должен запускаться в предсказуемом месте: на выделенном Linux-сервере или виртуальной машине. Это не обязательно мощный отдельный сервер, но он должен быть управляемым. На нём должны быть установлены нужные версии инструментов и должен работать GitLab Runner.

Ключевой шаг — связать Flutter Aurora SDK с установленным PSDK. Без этой настройки Flutter-часть не поймёт, где находится платформенное окружение Авроры. Команда указывает путь к PSDK, и дальше сборка может обращаться к нужным toolchain и target-файлам.

## Слайд 23. Кто выполняет pipeline

### Перенесённый текст из исходного документа

**Исходный документ, слайд 29. Кто выполняет pipeline**

Pipeline выполняет GitLab Runner. Это отдельный компонент, который подключается к GitLab, получает задачи и запускает их на выбранной машине. Если GitLab — это место, где описан процесс, то Runner — исполнитель, который реально выполняет команды из pipeline.

**Исходный документ, слайд 31. Регистрация runner**

Регистрация runner начинается с команды gitlab-runner register. На этом шаге мы говорим GitLab Runner, что хотим подключить новую машину к GitLab. Пока это только начало команды, дальше к ней добавляются параметры: адрес платформы, токен, имя и способ запуска.

sudo gitlab-runner register \

**Исходный документ, слайд 32. Регистрация runner**

Первый важный параметр — --url. Он указывает, к какому GitLab подключается runner. Это может быть gitlab.com или внутренняя GitLab-инсталляция компании. Если адрес указан неверно, runner просто не сможет получить задачи из нужного проекта.

sudo gitlab-runner register \

  --url https://gitlab.com/ \                        # адрес Git-платформы

**Исходный документ, слайд 33. Регистрация runner**

Следующий параметр — registration token. Он нужен, чтобы GitLab понял, что runner имеет право подключиться к проекту или группе. С точки зрения безопасности это важный момент: случайная машина не должна становиться исполнителем pipeline без разрешения.

sudo gitlab-runner register \

  --url https://gitlab.com/ \                        # адрес Git-платформы 

  --registration-token <TOKEN> \                     # токен регистрации

**Исходный документ, слайд 34. Регистрация runner**

Параметр --name задаёт понятное имя runner. В примере это aurora_flutter_runner, и по названию сразу видно его назначение. В реальной инфраструктуре имена важны: когда runner несколько, по ним проще понимать, какой отвечает за Flutter, Docker или другие задачи.

sudo gitlab-runner register \

  --url https://gitlab.com/ \                        # адрес Git-платформы 

  --registration-token <TOKEN> \                     # токен регистрации 

  --name aurora_flutter_runner \                     # имя runner’а

**Исходный документ, слайд 35. Регистрация runner**

Параметр --executor shell означает, что команды job будут выполняться прямо в оболочке сервера. Это простой вариант для начала: runner использует уже установленное окружение хоста. Минус такого подхода в том, что состояние сервера становится частью результата сборки.

sudo gitlab-runner register \

  --url https://gitlab.com/ \                        # адрес Git-платформы 

  --registration-token <TOKEN> \                     # токен регистрации 

  --name aurora_flutter_runner \                     # имя runner’а 

  --executor shell \                                 # запуск jobs на хосте

**Исходный документ, слайд 36. Регистрация runner**

Последний параметр здесь — --tag-list. Тег связывает job с конкретным runner. Это нужно, чтобы сборка Авроры не попала на случайную машину без PSDK. Для аудитории вопрос: что будет, если тяжелую платформенную сборку запустить на неподготовленном runner?

sudo gitlab-runner register \

  --url https://gitlab.com/ \                        # адрес Git-платформы 

  --registration-token <TOKEN> \                     # токен регистрации 

  --name aurora_flutter_runner \                     # имя runner’а 

  --executor shell \                                 # запуск jobs на хосте

  --tag-list aurora_flutter_runner                   # привязка jobs к нужному runner’у 

**Исходный документ, слайд 37. Зачем нужны tags**

Tags защищают pipeline от запуска в неподходящем окружении. Если job требует Flutter Aurora SDK и PSDK, она должна попасть именно на runner с такими инструментами. Без tags GitLab может выбрать другой доступный runner, и ошибка будет связана не с кодом, а с инфраструктурой.

**Исходный документ, слайд 38. Сохранение настроек**

После регистрации настройки runner сохраняются в config.toml. Здесь видно имя, адрес GitLab и тип executor. Этот файл важен при сопровождении: если сборка внезапно меняет поведение, стоит проверить не только .gitlab-ci.yml, но и конфигурацию самого runner.

[[runners]]

name = "aurora_psdk_runner"

url = "https://gitlab.com/"

executor = "shell"

## Слайд 24. Общая схема процесса

### Перенесённый текст из исходного документа

**Исходный документ, слайд 41. Общая схема процесса**

Общая схема такая: commit или merge request попадает в GitLab CI, GitLab выбирает runner, runner использует SDK или Docker-образ, выполняет стадии pipeline и сохраняет artifacts. Если объяснять процесс новичку, эта схема помогает показать, где заканчивается код и начинается инфраструктура.

**Исходный документ, слайд 42. Три основные стадии**

В нашем pipeline три основные стадии: build, sign и validation. Build создаёт RPM-пакет, sign добавляет подпись, validation проверяет готовый результат. Такой порядок удобен: каждый следующий шаг работает с результатом предыдущего, а не пересобирает приложение заново.

**Исходный документ, слайд 43. Почему разделяем этапы**

Разделение этапов упрощает диагностику. Если упала сборка, мы смотрим build job. Если проблема с сертификатом, проверяем sign. Если пакет не проходит требования платформы, анализируем validation. Один этап — одна зона ответственности, поэтому pipeline легче поддерживать.

## Слайд 25. Build job

### Перенесённый текст из исходного документа

**Исходный документ, слайд 44. Build job**

Начинаем с build job. Здесь задаётся имя задачи, стадия build, тег нужного runner и список артефактов. Пока в job нет команд сборки, но уже видно главное: всё, что попадёт в ./artifacts/*.rpm, GitLab должен сохранить после выполнения.

"build-aurora-flutter_aarch64":

  stage: build

  tags:

    - aurora_flutter_runner

  artifacts:

    paths:

      - ./artifacts/*.rpm

**Исходный документ, слайд 45. Build job**

Теперь добавляется секция script и первая команда — создание директории artifacts. Это простая подготовка места, куда позже будет скопирован RPM. Такой шаг лучше делать явно, чтобы job не зависела от того, есть ли эта папка в репозитории заранее.

"build-aurora-flutter_aarch64":

  stage: build

  tags:

    - aurora_flutter_runner

  artifacts:

    paths:

      - ./artifacts/*.rpm

  script:

    - mkdir -p artifacts

**Исходный документ, слайд 46. Build job**

Следующая команда — flutter pub get. Она подтягивает зависимости проекта перед сборкой. Это важный момент: pipeline должен сам подготавливать проект, а не рассчитывать, что зависимости уже есть на сервере. Так сборка становится чище и понятнее по логам.

"build-aurora-flutter_aarch64":

  stage: build

  tags:

    - aurora_flutter_runner

  artifacts:

    paths:

      - ./artifacts/*.rpm

  script:

    - mkdir -p artifacts

    - /flutter-aurora/bin/flutter pub get

**Исходный документ, слайд 47. Build job**

Здесь появляется основная команда сборки. Мы запускаем flutter build aurora, указываем release-режим и target-платформу aurora-arm64. Это уже не универсальная Flutter-сборка, а конкретная сборка под Аврору и выбранную архитектуру.

"build-aurora-flutter_aarch64":

  stage: build

  tags:

    - aurora_flutter_runner

  artifacts:

    paths:

      - ./artifacts/*.rpm

  script:

    - mkdir -p artifacts

    - /flutter-aurora/bin/flutter pub get

    - /flutter-aurora/bin/flutter build aurora --release --target-platform aurora-arm64

**Исходный документ, слайд 48. Build job**

Последняя команда копирует готовые RPM-файлы в директорию artifacts. Путь содержит ${PSDK_VER}, потому что результат лежит внутри каталога конкретной версии PSDK. Если этот шаг пропустить, пакет может собраться, но GitLab не сохранит его как скачиваемый артефакт.

"build-aurora-flutter_aarch64":

  stage: build

  tags:

    - aurora_flutter_runner

  artifacts:

    paths:

      - ./artifacts/*.rpm

  script:

    - mkdir -p artifacts

    - /flutter-aurora/bin/flutter pub get

    - /flutter-aurora/bin/flutter build aurora --release --target-platform aurora-arm64

    - cp build/aurora/psdk_${PSDK_VER}/aurora-arm64/release/RPMS/*.rpm ./artifacts/

## Слайд 26. Задание переменной PSDK_VER

### Перенесённый текст из исходного документа

**Исходный документ, слайд 49. Задание переменной PSDK_VER**

Переменная PSDK_VER нужна, чтобы не зашивать версию PSDK прямо в команды. Это удобнее при обновлениях: меняется значение переменной, а структура job остаётся той же. Такой подход снижает количество правок в .gitlab-ci.yml.

**Исходный документ, слайд 50. Задание переменной PSDK_VER**

В пути сборки версия PSDK используется для поиска итогового RPM. Поэтому переменная должна совпадать с реально установленной версией окружения. Если значение неправильное, сборка может пройти, но копирование артефакта завершится ошибкой, потому что нужный каталог не будет найден.

**Исходный документ, слайд 51. Результат build**

После успешного build у нас есть готовый RPM-пакет, но пока это только результат сборки. Его ещё нельзя считать полностью подготовленным к поставке, потому что впереди подпись и проверка. На этом этапе важно убедиться, что GitLab сохранил пакет в artifacts.

## Слайд 28. Sign job

### Перенесённый текст из исходного документа

**Исходный документ, слайд 52. Sign job**

Переходим к sign job. Она находится на стадии sign и запускается после build. Через needs и dependencies мы явно связываем её с предыдущей задачей. Это значит, что подпись работает не с исходным кодом, а с RPM, который уже был собран.

"sign-aurora-flutter_aarch64":

  stage: sign

  tags:

    - aurora_flutter_runner

  needs:

    - "build-aurora-flutter_aarch64"

  dependencies:

    - "build-aurora-flutter_aarch64"

  artifacts:

    paths:

      - ./artifacts/*.rpm

**Исходный документ, слайд 53. Sign job**

В script вызывается rpmsign-external sign через sdk-chroot. Команде передаются ключ и сертификат выбранного профиля подписи, а входом служат RPM-файлы из artifacts. Практически это превращает неподписанный пакет в пакет, который можно дальше проверять и использовать.

"sign-aurora-flutter_aarch64":

  stage: sign

  tags:

    - aurora_flutter_runner

  needs:

    - "build-aurora-flutter_aarch64"

  dependencies:

    - "build-aurora-flutter_aarch64"

  artifacts:

    paths:

      - ./artifacts/*.rpm

  script:

    - /path/to/AuroraPlatformSDK/sdks/sdk-chroot rpmsign-external sign

      -k ~/aurora-profiles/${SIGN_PROFILE}/key.pem

      -c ~/aurora-profiles/${SIGN_PROFILE}/cert.pem

      ./artifacts/*.rpm

## Слайд 34. Что такое Docker-образ

### Перенесённый текст из исходного документа

**Исходный документ, слайд 60. Почему нужен Docker**

Docker нужен, чтобы зафиксировать сборочную среду. В образ можно положить системные зависимости, PSDK, Flutter Aurora SDK и базовые настройки. Тогда job запускается внутри контейнера, а не в текущем состоянии сервера. Это уменьшает влияние ручных изменений на хосте.

**Исходный документ, слайд 61. Что такое Docker-образ**

Docker-образ — это шаблон среды выполнения. Он содержит файловую систему, зависимости, переменные окружения и инструкции запуска. На основе образа создаются контейнеры, где выполняются команды pipeline. Один и тот же образ можно использовать и в CI, и для локальной проверки сборки.

## Слайд 35. Как Docker решает наши проблемы

### Перенесённый текст из исходного документа

**Исходный документ, слайд 62. Преимущество №1**

Первое преимущество Docker-образа — воспроизводимость. Один и тот же код собирается в одном окружении, а не на разных серверах с разными настройками. Если сборка упала, мы проверяем код, версию образа и логи, а не пытаемся угадать состояние машины.

**Исходный документ, слайд 63. Преимущество №2**

Второе преимущество — изоляция. Инструменты сборки находятся внутри контейнера и меньше влияют на хост-систему. Это особенно полезно, когда на одном сервере работают разные проекты: зависимости одного проекта не должны случайно ломать сборку другого.

**Исходный документ, слайд 64. Преимущество №3**

Третье преимущество — версионирование SDK через tag образа. Например, можно хранить отдельные образы под разные версии Flutter Aurora SDK или PSDK. Тогда переход на новую версию окружения становится управляемым: меняем tag, проверяем pipeline и при необходимости откатываемся.

## Слайд 36. Dockerfile: настройка окружения

### Перенесённый текст из исходного документа

**Исходный документ, слайд 65. Dockerfile: общая идея**

Dockerfile описывает, из чего состоит сборочная среда. Обычно начинается с базовой ОС, затем устанавливаются системные зависимости, добавляется Aurora PSDK, после этого Flutter Aurora SDK. Важно, что эта инструкция хранится как код и может проходить ревью вместе с проектом.

**Исходный документ, слайд 66. Dockerfile: настройка окружения**

В начале Dockerfile задаётся базовый образ Ubuntu, домашняя директория и PATH, чтобы команды Flutter Aurora были доступны без полного пути. Затем устанавливаются минимальные системные зависимости. Очистка apt-кэша нужна, чтобы образ не становился больше без необходимости.

FROM ubuntu:22.04

ENV HOME="/home/docker"

ENV PATH="$HOME/.local/opt/flutter-aurora/bin:$HOME/.local/bin:$PATH"

RUN apt-get update && apt-get install -y --no-install-recommends sudo tar && rm -rf /var/lib/apt/lists/*

**Исходный документ, слайд 67. Dockerfile: пользователь**

Здесь создаётся отдельный пользователь docker, которому разрешается выполнять sudo без пароля. После этого контейнер переключается на этого пользователя, а рабочей директорией становится его home. Это делает среду более предсказуемой, чем выполнение всех команд от root.

RUN useradd -rm -d $HOME -s /bin/bash -g root -G sudo -u 1001 docker && \

    echo 'docker ALL=(ALL) NOPASSWD:ALL' > /etc/sudoers.d/docker && \

    chmod 0440 /etc/sudoers.d/docker

USER docker

WORKDIR $HOME

## Слайд 37. Dockerfile: установка SDK

### Перенесённый текст из исходного документа

**Исходный документ, слайд 68. Dockerfile: установка SDK**

На этом шаге в контейнер копируется каталог installers. В нём должны лежать установочные файлы Aurora Platform SDK и архив Flutter Aurora SDK. Опция --chown сразу задаёт владельца файлов, чтобы дальше пользователь docker мог с ними работать без проблем с правами.

COPY --chown=docker:root installers/ /tmp/installers/

**Исходный документ, слайд 69. Dockerfile: установка SDK**

Теперь запускается установка Aurora PSDK. Скрипту передаётся каталог с исходными установочными файлами и каталог, куда нужно установить SDK. После этого внутри контейнера появляется платформенное окружение, которое будет использоваться при сборке RPM под Аврору.

COPY --chown=docker:root installers/ /tmp/installers/

RUN sudo /bin/bash /tmp/installers/install_aurora_psdk.sh \

    --input-dir /tmp/installers/AuroraPlatformSDK \

    --install-dir $HOME/AuroraPlatformSDK

**Исходный документ, слайд 70. Dockerfile: установка SDK**

Последний блок устанавливает Flutter Aurora SDK: создаёт каталоги, распаковывает архив, делает ссылку flutter-aurora и связывает SDK с PSDK. После этого образ уже содержит все основные инструменты. Практический результат: job может запускать сборку без ручной настройки сервера.

COPY --chown=docker:root installers/ /tmp/installers/

RUN sudo /bin/bash /tmp/installers/install_aurora_psdk.sh \

    --input-dir /tmp/installers/AuroraPlatformSDK \

    --install-dir $HOME/AuroraPlatformSDK

RUN mkdir -p "$HOME/.local/opt/flutter-aurora" "$HOME/.local/bin" && \

    tar -xf /tmp/installers/flutter-aurora.tar.xz \

      --strip-components=1 \

      -C "$HOME/.local/opt/flutter-aurora" && \

    ln -s "$HOME/.local/opt/flutter-aurora/bin/flutter" "$HOME/.local/bin/flutter-aurora" && \

    flutter-aurora config --aurora-psdk-dir "$HOME/AuroraPlatformSDK/sdks/aurora_psdk"

## Слайд 38. GitLab Container Registry

### Перенесённый текст из исходного документа

**Исходный документ, слайд 71. GitLab Container Registry**

После написания Dockerfile образ нужно собрать. Команда docker build создаёт образ и сразу задаёт ему имя в формате GitLab Container Registry. В tag можно использовать latest для примера, но в рабочих проектах лучше указывать версию окружения явно.

docker build -t registry.gitlab.com/<group>/<project>/flutter-aurora:latest .

**Исходный документ, слайд 72. GitLab Container Registry**

После сборки образ публикуется командой docker push. С этого момента он хранится в GitLab Container Registry и может использоваться runner-ом. Это удобно: образ собирается один раз, а потом одинаково применяется в pipeline разных веток или проектов.

docker build -t registry.gitlab.com/<group>/<project>/flutter-aurora:latest .

docker push registry.gitlab.com/<group>/<project>/flutter-aurora:latest

## Слайд 39. Docker Runner

### Перенесённый текст из исходного документа

**Исходный документ, слайд 73. Gitlab Runner**

Теперь runner можно настроить как Docker executor. В отличие от shell executor, job будет запускаться не прямо на хосте, а внутри контейнера. Это меняет модель работы: сервер предоставляет Docker, а конкретная сборочная среда берётся из подготовленного образа.

[[runners]]

  name = "aurora-docker"

  executor = "docker"

**Исходный документ, слайд 74. Gitlab Runner**

Для работы PSDK внутри контейнера может потребоваться привилегированный режим. Параметр privileged = true расширяет возможности контейнера. Это не настройка «для красоты», а техническое требование для сценариев, где сборочная среда обращается к системным механизмам хоста.

[[runners]]

  name = "aurora-docker"

  executor = "docker"

  [runners.docker]

    privileged = true                                                      # привилегированный режим

**Исходный документ, слайд 75. Gitlab Runner**

Здесь runner дополнительно пробрасывает ресурсы хоста: модули ядра, D-Bus, machine-id и данные D-Bus. Это нужно, чтобы инструменты внутри контейнера могли корректно работать с PSDK. Важно: Docker фиксирует окружение, но не отменяет требований платформенных инструментов.

[[runners]]

  name = "aurora-docker"

  executor = "docker"

  [runners.docker]

    privileged = true                                                      # привилегированный режим

    volumes = [                                                            # проброс ресурсов хоста

      "/lib/modules:/lib/modules:ro",                                      # модули ядра

      "/run/dbus/system_bus_socket:/run/dbus/system_bus_socket",           # системный D-Bus

      "/var/run/dbus:/var/run/dbus:ro",                                    # сокеты D-Bus

      "/etc/machine-id:/etc/machine-id:ro",                                # machine-id

      "/var/lib/dbus:/var/lib/dbus:ro"                                     # данные D-Bus 

    ]
